# Business Rules — fortune-bot

## BR-1: 文字数制限

| ルール | 内容 |
|--------|------|
| 最大文字数 | **149 rune**（MIXI2 API 制約） |
| カウント単位 | `len([]rune(text))`（バイト数ではない） |
| 改行文字 | `\n` は **1 rune** としてカウントする |

---

## BR-2: 投稿フォーマット

- **1行目**: `{trait}、{state}{zodiac}のあなた、今日、{verdict}。`
- **2行目**: `ラッキー行動：{ritual}`
- 1行目と2行目は `\n`（改行）で結合する

---

## BR-3: トリミング優先順位

文字数が 149 rune を超えた場合、以下の順で対応する。

| 優先度 | 対応 | 理由 |
|--------|------|------|
| 1 | trait（特徴）を削除 | state の方が「今この瞬間感」があり刺さりやすい |
| 2 | state（状態）も削除 | 最小形でも成立するため |
| 3（最終手段） | line1 最小形 + ritual を rune 単位で末尾 `…` 短縮 | 辞書設計で防ぐべきケース |

**最小形**: `{zodiac}のあなた、今日、{verdict}。\nラッキー行動：{ritual}`

**Step 3 の制約**:
- `ラッキー行動：` と改行は **必ず維持**（line2 の構造を壊さない）
- ritual のみを rune 単位で切り詰め `…` を付加（line2 が途中で消えるケースを排除）
- 全体カットで改行が消えたり「ラッキー行動：」だけ残る状態は発生させない

---

## BR-4: 辞書エントリの文字数制約

辞書設計で BR-3 の最終手段（Step 3）が発生しないようにする。

| フィールド | 最大文字数 | 理由 |
|-----------|-----------|------|
| zodiac | 4 rune | 例: 水瓶座 |
| state | 20 rune | 例: 今コーヒーをこぼしている |
| trait | 20 rune | 例: あごひげをたくわえていて |
| verdict | 25 rune | 例: 運勢が一回だけ成仏します |
| ritual | 40 rune | 例: コップの水に...（1文で収める） |

**最大文字数の根拠（最小形での最悪ケース計算）:**
```
zodiac(4) + "のあなた、今日、"(8) + verdict(25) + "。"(1) + "\n"(1)
+ "ラッキー行動："(7) + ritual(40)
= 4 + 8 + 25 + 1 + 1 + 7 + 40 = 86 rune → 149 以内 ✅

フル形（trait + state 込み）:
trait(20) + "、"(1) + state(20) + 86 = 127 rune → 149 以内 ✅
```

**辞書エントリの文体ルール（崩れ防止）:**

| フィールド | 末尾のルール | 例 |
|-----------|------------|-----|
| trait | `〜で` / `〜していて` / `〜な` で終わる | あごひげをたくわえていて／左利きで |
| state | `今〜している` の形にする | 今歯をみがいている／今コーヒーを飲んでいる |

文体ルールを守ることで `{trait}、{state}{zodiac}のあなた…` の自然な接続を保証する。

**起動時バリデーション（`LoadDictionary()` 内で実施）:**
- 各エントリが上記 rune 上限を超えていれば `os.Exit(1)`
- 各辞書のエントリ数が 1 件未満なら `os.Exit(1)`
- 最悪ケース合成（最大長エントリを組み合わせたフル形）を 1 回計算し `len([]rune())` をログ出力する

---

## BR-5: トーン制約

| ルール | 内容 |
|--------|------|
| 禁止表現 | ユーザー本人に対して「死ぬ」「消える」等の断定は使わない |
| 推奨表現 | 「運勢が成仏する」「不運が転生する」「現実がログアウトする」などの間接的表現 |
| 方向性 | めちゃスピリチュアルで、やりすぎて面白い方向に振り切る |

---

## BR-6: 辞書エントリ数

| 要件 | 内容 |
|------|------|
| 初期エントリ数 | 各辞書 **20〜30件** |
| 理由 | 5分おき投稿でのローテーション耐性（少なすぎると繰り返しが見えやすい） |

---

## BR-7: エラーハンドリング

| 状況 | 対応 |
|------|------|
| 辞書 JSON のパース失敗 | エラーログ出力 → `os.Exit(1)` |
| 辞書が空（エントリ0件） | エラーログ出力 → `os.Exit(1)` |
| MIXI2 API 投稿失敗 | エラーログ出力 → `os.Exit(1)`（GitHub Actions でジョブ失敗として記録） |
| レート制限超過 | エラーログ出力 → `os.Exit(1)`（リトライなし） |
| 辞書エントリの rune 長超過 | エラーログ出力 → `os.Exit(1)`（起動時バリデーション） |
| 辞書エントリ数 0 件 | エラーログ出力 → `os.Exit(1)`（起動時バリデーション） |

**GitHub Actions 多重起動対策:**
`fortune.yml` に `concurrency` を設定し、同じワークフローが二重に走らないようにする。
レート制限超過の主因は二重起動であるため、Actions 側で防ぐ。

```yaml
concurrency:
  group: fortune-bot
  cancel-in-progress: true
```

---

## BR-8: ログ出力

投稿前に生成した本文をログに出力する。

```
log.Printf("posting: %s", text)
```

GitHub Actions のログで投稿内容を確認できるようにする。
